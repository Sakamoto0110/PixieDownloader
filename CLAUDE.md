# PixieDownloader

App desktop **WPF / .NET 10** (Windows) — GUI para o `yt-dlp` baixar áudio (MP3) ou vídeo (MP4). Tema dark purple, janela custom (WindowChrome).

## Comandos
- Build: `dotnet build PixieDownloader.slnx -v q --nologo`
- Rodar o app: `dotnet run --project src/PixieDownloader -c Release`
- Testes (xunit; `dotnet test PixieDownloader.slnx` roda os dois projetos):
  - `tests/YtDlpCore.Tests` (`net10.0`) — `YtDlpOutputParser`, `OutputTemplate`, `PendingQueueFile`, `MetadataFields`, `TracklistExtractor` via fixtures: `dotnet test tests/YtDlpCore.Tests`
  - `tests/PluginHost.Tests` (`net10.0-windows`, referencia o app) — o host de plugins de ponta a ponta: copia o Hello buildado pra uma `plugins/` temporária e passa pelo `PluginCatalog` como o app faz (cast pelo ALC, capacidades, disable/enable, recusas, dependências, uninstall, view XAML numa thread STA), mais `SdkVersion`: `dotnet test tests/PluginHost.Tests`
  - Um teste só: `dotnet test tests/YtDlpCore.Tests --filter "FullyQualifiedName~TryParseProgress_parses_percent_speed_eta"`
- Publish (sempre um `PixieDownloader.exe` único, dois sabores via profile em `src/PixieDownloader/Properties/PublishProfiles/`):
  - Framework-dependent (~1 MB, exige o .NET 10 Desktop Runtime na máquina) → `bin/publish/framework-dependent/`: `dotnet publish src/PixieDownloader/PixieDownloader.csproj -c Release -p:PublishProfile=FrameworkDependent`
  - Self-contained (~62 MB, roda em Windows pelado — é este o "portátil" para distribuir) → `bin/publish/self-contained/`: `dotnet publish src/PixieDownloader/PixieDownloader.csproj -c Release -p:PublishProfile=SelfContained`
- SDK de plugins como pacote: `dotnet pack src/PixieDownloader.Sdk/PixieDownloader.Sdk.csproj -c Release -o bin/release/` → `PixieDownloader.Sdk.<apiVersion>.nupkg` (um pacote só: `PixieDownloader.Sdk.dll` + `YtDlpCore.dll` + XML docs em `lib/net10.0-windows7.0/`, sem dependências). O `release.ps1` já faz isso.
- Release (os dois `.zip` + o `.nupkg` que vão pro GitHub, montados do zero em `bin/release/`): `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/release.ps1` (`-Flavor normal|portable`, `-SkipTests`). Faz restore/build/test, publica os dois profiles, empacota o SDK (`--no-build`, do mesmo build testado) e gera `PixieDownloader-vX.Y.Z-win-x64.zip` (~1 MB, precisa do .NET 10 Desktop Runtime), `…-portable.zip` (~57 MB, self-contained), `PixieDownloader.Sdk.A.B.C.nupkg`, `SHA256SUMS.txt` e `RELEASE_NOTES.md`. Cada zip abre em `PixieDownloader\` com `.exe`, `LICENSE` e `LEIA-ME.txt` — **sem yt-dlp/ffmpeg de propósito** (o app baixa os dois na primeira abertura; assim a release não redistribui o binário GPL do ffmpeg) e sem cache/logs/settings/staging.
  - Publicar: bump `<Version>` no `.csproj`, `git tag vX.Y.Z && git push origin vX.Y.Z` → `.github/workflows/release.yml` (runner `windows-2025`, actions fixadas por SHA, SDK 10.0.400 — também cravado em `global.json` com `latestPatch`, então um SDK 10.0.5xx da máquina não é usado por engano) roda o mesmo script e cria a GitHub Release via `gh` com os assets. O script recusa se o tag não bater com o `<Version>`.
- Smoke test de ponta a ponta (offline + online opcional; fecha a instância em execução, builda, faz boot test e roda o harness): `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/smoke.ps1`
  - `src/SmokeTest` **não está na `.slnx`** e não é referenciado pelo app — existe só pra exercitar `YtDlpService.BuildSpeedPassArgs`/o pipeline de vídeo via `InternalsVisibleTo`. Harness B (online) só roda se `test.txt` (raiz do repo, git-ignored) tiver uma URL.

## Versionamento
- A versão mora **só** em `<Version>` no `src/PixieDownloader/PixieDownloader.csproj` (hoje `1.4.0`). Dela saem o FileVersion/ProductVersion do `.exe`, o selo `v1.4.0` no header (`AppInfo.cs`; ao lado, o ícone do GitHub abre `AppInfo.RepositoryUrl`) e o User-Agent `PixieDownloader/1.4.0` do `YtDlpService` (passado pelo `App.xaml.cs`; sem ele o UA é `PixieDownloader/dev`). Bump antes de cortar release.
- Histórico publicado no GitHub: **1.0** (tag `Stable`, 2026-07-05) e **1.3** (tags `Net10` = framework-dependent e `Portable` = self-contained, 2026-07-27). As tags não carregam o número — o título da release é que diz a versão; `gh release list` mostra. Minor por feature (1.1 playlist/staging, 1.2 modo vídeo + import, 1.3 trim/GIF); a fila de downloads é a 1.4.
- **O SDK tem versão própria** (`<Version>` em `src/PixieDownloader.Sdk/PixieDownloader.Sdk.csproj`, hoje `1.0.0`): é o `apiVersion` que os plugins declaram no `plugin.json` e a versão do `.nupkg`. `SdkVersion.Current` lê de volta do assembly. Membro novo numa interface pública do Sdk = minor; mudar/remover = major. Pode mudar numa release de app que seja só patch.

## Roadmap
- `docs/ROADMAP.md` (com `docs/pixie-arch.png`) é o plano 1.5 → 1.8: o app não cresce — tudo além do download vira **plugin** carregado em runtime via `PixieDownloader.Sdk`, nenhum plugin conhece outro. 1.5 = só o SDK + loader + plugin de teste; 1.6 = o extractor de tracklist vira plugin; 1.7 = tracklist aninhada; 1.8 = discovery. As decisões de design já tomadas (Sdk referencia o core, `YtDlpCore` também é assembly compartilhado no ALC, Sdk dentro do exe e distribuído como um `.nupkg` só) estão lá — ler antes de mexer em plugin.

## Estrutura
- `src/YtDlpCore/` — biblioteca core (`net10.0`, **sem WPF**): serviço do yt-dlp, parser, settings, logger, cache de thumbnail. Gera XML docs (vão no pacote do SDK).
- `src/PixieDownloader.Sdk/` — o contrato de plugin (`net10.0-windows` + WPF, referencia o core): `IPixiePlugin`, `IPluginHost`, `IUiContribution`, `PluginManifest`, `SdkVersion`. O app referencia (vai dentro do `.exe` single-file); plugins de fora consomem o `.nupkg` com `ExcludeAssets="runtime"`. `README.md` do projeto é o readme do pacote (csproj de plugin, `plugin.json`, plugin mínimo).
- `src/PixieDownloader/` — app WPF (`net10.0-windows`): Views, ViewModels, tema, e o host de plugins em `Plugins/` (`PluginCatalog`, `PluginLoadContext`, `PluginHost`, `CapabilityRegistry`, `InstalledPlugin`).
- `src/Plugins/Pixie.Hello/` — o plugin de prova da 1.5 (aba XAML, chamada em `IYtDlpService`, capacidade `hello.greet`; `QuietPlugin` é o entry type mudo dos testes). Dev-only: o app não referencia, a release não leva; um target pós-build espelha em `src/PixieDownloader/bin/<cfg>/net10.0-windows/plugins/hello/` pra `dotnet run` mostrar a aba.
- `src/SmokeTest/` — harness de fumaça dev-only (veja acima).
- `tests/YtDlpCore.Tests/` — testes do parser e dos helpers puros do core (template, arquivo de pendências, metadados, tracklist).
- `tests/PluginHost.Tests/` — testes do host de plugins (veja Comandos).
- Solução: `PixieDownloader.slnx` (core, Sdk, app, `Plugins/Pixie.Hello` e os dois projetos de teste; `SmokeTest` fica de fora de propósito).

## Arquitetura
- **`IYtDlpService` é a única fronteira que a UI WPF conhece** — nenhum `Process` é chamado fora de `YtDlpCore`. `YtDlpService` compõe `YtDlpProcessRunner` (exec + captura de stdout/stderr), `BinaryManager` (resolve/baixa/atualiza `yt-dlp`/`ffmpeg` de `./tools/` ou do PATH), `UpdateChecker` e `ThumbnailCache`. Toda operação é async/cancelável e emite `LogEntry` via evento `LogEmitted` (consumido pela aba de logs) além de persistir no `SessionLogger`, se houver.
- **Pipeline de download de vídeo com passo de ffmpeg** (`YtDlpService.DownloadAsync`/`PostProcessAndDeliverAsync`): quando o vídeo precisa de mudança de velocidade, GIF ou de "vídeo mudo + mp3 separado" (`VideoOptions.NeedsFfmpegPass`), o yt-dlp baixa para a pasta privada do job (`home` e `temp` do yt-dlp apontam pra lá) em vez do diretório de saída final. Depois, os arquivos são localizados no disco por extensão (não por parsing do log — robusto a título com emoji/Unicode), processados com um passo de `ffmpeg` próprio (`BuildSpeedPassArgs`: `setpts` pro vídeo, `atempo` encadeado pro áudio — o `--recode` do yt-dlp faz no-op num arquivo já `.mp4`, então não dá pra confiar nele) e só então movidos pra pasta de saída real, preservando as subpastas do template. O passo reporta `DownloadStage.Processing` com `%` (ffmpeg `-progress pipe:1` × `DownloadRequest.SourceDuration`) e um `Detail` por sub-etapa.
- **Staging por job**: cada `DownloadAsync` cria `.~downloads/job-<guid>/` (ao lado do `.exe`) e apaga no `finally` (com retry — o processo morto no cancel pode segurar handle por um instante). Um `.~downloads/` não vazio na abertura = sessão anterior morreu no meio: `MainViewModel.InitializeAsync` avisa (banner) e chama `IYtDlpService.PurgeStaging()`. `cache/` só tem thumbnails (LRU) e não é limpo.
- **Fila de downloads** (`MainViewModel`, seção `Fila de downloads` + `DownloadJobViewModel`): "Baixar" não chama o serviço direto — vira jobs. Cada item selecionado é um `DownloadRequest` próprio (item de playlist baixa pela URL direta do vídeo, com os tokens `%(playlist_title)s`/`%(playlist_index)s` substituídos por literais via `OutputTemplate.SubstituteLiteral`; vídeo avulso usa `WithoutPlaylistTokens`). Um request que precisa do passo de ffmpeg vira **duas linhas vinculadas** (download → processamento, mesmo `RequestId`, movem juntas no drag-and-drop de `QueuePanel`). O runner (`PumpQueue`) inicia jobs em ordem da lista até `Settings.Advanced.ParallelDownloads`; tudo roda na UI thread (progresso via `Progress<T>`). "Cancelar" na aba principal cancela o **primeiro item em andamento**; cada linha tem Cancelar/Remover; a aba tem Limpar concluídos / Cancelar todos.
- **Pendências persistentes**: `pending-downloads.txt` ao lado do `.exe` (`PendingQueueFile`, 1 JSON por linha, aceita linha só com URL) reescrito com debounce a cada mudança enquanto `Settings.Ui.QueuePersistent` estiver ligado. Ao fechar, `ShutdownAsync` marca as linhas em andamento (`InterruptedByShutdown`), liga `IYtDlpService.KeepWorkDirsOnCancel`, cancela, espera até 4s e só então grava o snapshot final (`IsShutdownPending`) e purga o staging poupando as pastas referenciadas. Na abertura, os jobs voltam como "restaurados" (não iniciam sozinhos): banner com Continuar/Descartar e o botão principal vira "Continuar downloads/processamento/pendências (N)".
- **Retomar só o processamento**: se o app fechou com o download pronto e o ffmpeg no meio, a pasta `job-…` sobrevive (só nesse caso — cancelar pelo usuário apaga tudo), a entrada da pendência ganha `workDirectory`, e o request volta com `DownloadRequest.ResumeWorkDirectory`: linha de download já "Baixado na sessão anterior", linha de processamento "interrompido — retoma daqui". `DownloadAsync` pula o yt-dlp, limpa os intermediários parciais (`.pixie.mp4`, `.speed.mp4`, palette, gif/mp3 parciais) e roda só o passo; se a pasta sumiu, avisa e baixa de novo. O re-encode em si recomeça do zero (ffmpeg não tem checkpoint). Rotulagem é honesta por etapa: falha/interrupção depois do download fica na linha de processamento, nunca na de download.
- **Tentar de novo**: linha falha/cancelada ganha o botão (`RetryJobCommand` → `ResetForRetry` nas duas linhas + `StartQueue`).
- **Metadados por campo** (`MetadataFields` no core + `MetadataItemViewModel`/`MetadataPanel`): a análise guarda em `VideoInfo.Metadata` os campos que o `--embed-metadata` do yt-dlp realmente embute; a sidebar lista cada um com checkbox + expander. Desmarcar um campo entra em `Settings.Audio.ExcludedMetadataFields` (persistido) e vira `--parse-metadata ":(?P<meta_TAG>)"` (idioma do yt-dlp pra deixar a tag vazia). O master tri-state espelha `Settings.Audio.EmbedMetadata`.
- **Detecção de tracklist** (`src/YtDlpCore/Tracklists/`, puro, sem WPF): a análise de vídeo único passa `fetchComments: true` (`--write-comments` + `youtube:comment_sort=top;max_comments=20,20,0,0`, +1–2 s; a resolução de lista importada passa `false`) e `VideoInfo` ganha `Description`/`Chapters`/`Comments`. `TracklistExtractor.Analyze(video)` é heurístico de propósito — não existe padrão de como as pessoas escrevem tracklist: `TracklistLine` classifica cada linha (NFKC + sem zero-width; tempo no início/fim/range, número, link de faixa vs. perfil/social/site de tracklist, cabeçalho em PT/EN/ES/FR/DE/RU/JA/ZH/KO, "cabeçalho de outra seção", divisor, hashtag), o extrator junta linhas da mesma família em blocos (tolerando link solto embaixo da faixa, "tempo numa linha / título na outra", sub-cabeçalho por set, linha em branco entre pares título/link), pontua cada bloco (cabeçalho, tempos crescentes, numeração, tags de remix, penalidades pra frases/textos repetidos/seção social) e escolhe o melhor entre descrição → comentário fixado → do canal → mais curtido; os `chapters` do yt-dlp são só candidato de fallback (o YouTube exige `0:00`, ≥3, crescente e tempo "pelado"). `TracklistReportFormatter` gera o texto (URL / ===== / título / ===== / achados) que `MainViewModel.ReportTracklist` joga na aba Debug depois de cada análise — por enquanto o resultado **só vai pra lá** (nada de `.txt` nem sidebar ainda). Corpus de verdade vira fixture em `tests/YtDlpCore.Tests/Fixtures/Tracklists/*.txt` (formato documentado em `TracklistExtractorTests`): padrão novo que errar = novo arquivo lá, sem tocar em código.
- **Plugins** (`src/PixieDownloader/Plugins/`, contrato em `src/PixieDownloader.Sdk/`): `App.xaml.cs` cria o `PluginCatalog` (`plugins/` e `data/` ao lado do `.exe`) e chama `Initialize()` **antes** da janela existir, na UI thread — cada `plugins/<id>/plugin.json` é lido sem carregar assembly (`PluginManifest`, 1:1 com o JSON), recusado com motivo nos logs se o id não bate com a pasta / `apiVersion` incompatível (`SdkVersion.IsCompatible`: mesmo major, minor ≤ o do host) / assembly ausente / `dependsOn` não atendido, e o resto carrega em ordem de dependência num `PluginLoadContext` próprio (collectible; `Load` devolve `null` pro Sdk e pro `YtDlpCore` — nomes tirados de `typeof(...).Assembly` — pra virem do Default ALC e serem o mesmo tipo dos dois lados). `EntryType` é instanciado por construtor vazio, castado pra `IPixiePlugin` e recebe um `PluginHost` (`Downloads`, `DataDirectory` criado no primeiro uso, `Log` com source `Plugin:<id>`, `ShutdownToken`, capacidades por id via `CapabilityRegistry` — id duplicado é erro de `Configure` → `Failed`). `MainWindow.WirePluginTabs` insere uma `TabItem` por `IUiContribution` depois de "Fila" (`Tag` = id) e reage a `PluginEnabled`/`PluginDisabled`; o VM assina `LogEmitted` do catálogo desde o construtor. **Desabilitar** é imediato (token cancelado, capacidades removidas, aba fora; o ALC fica — WPF não descarrega) e persiste em `Settings.Plugins.DisabledIds`; dependentes caem junto e voltam no `Enable`. **Desinstalar** grava `plugins/<id>/.uninstall` e a pasta some no próximo `Initialize` (arquivo em uso até o processo morrer); `CancelUninstall` desfaz e deixa desabilitado. `data/<id>/` nunca é apagado pelo host. Plugin com XAML usa `DynamicResource` pros estilos do host (a view nasce fora da árvore). A UI de gerenciar (aba Plugins) ainda não existe — é o passo 5 da 1.5.
- **Logs**: `LogEmitted` chega de threads de pump; o VM enfileira num `ConcurrentQueue` e drena em lote no dispatcher (`Background`), com ring buffer de 1000 entradas na UI (o `SessionLogger` continua gravando tudo em disco).
- **Rescale da janela**: abaixo de 940×560 (`MainWindow.UpdateScale`) o `Grid` raiz recebe um `LayoutTransform` de escala uniforme (mínimo real 620×420) em vez de recortar o layout.
- **`MainViewModel` é um VM único e grande** (`src/PixieDownloader/ViewModels/MainViewModel.cs`, ~2000 linhas) que cobre todas as abas do app: análise/playlist, seleção por range, montagem incremental do template de saída (stack de tokens), fila de downloads, importação (.txt / colar links), metadados, aba de debug (comandos crus do yt-dlp) e aba de logs. Ao adicionar uma feature de UI, o padrão é uma nova seção comentada (`// ───── Nome ─────`) dentro desse mesmo arquivo, não um VM novo. VMs de linha pequenos (`PlaylistItemViewModel`, `DownloadJobViewModel`, `MetadataItemViewModel`) ficam em arquivos próprios.
- **Single instance**: `App.xaml.cs` usa um `Mutex` nomeado + `EventWaitHandle` pra focar a janela existente em vez de abrir uma segunda instância.
- **Settings com auto-save**: `SettingsService` assina `PropertyChanged` de todos os nós de `AppSettings` (`Ui`, `Paths`, `Audio`, `Video`, `Advanced`, `Tools`, `RecentUrls`) e agenda um save debounced (500ms) a cada mudança; salva em `settings.json` com backup (`settings.json.bak`) e fallback pro backup se o arquivo principal estiver corrompido no load.

## Convenções / decisões já tomadas
- **MVVM escrito à mão (sem CommunityToolkit.Mvvm).** Base `ObservableObject` em `src/YtDlpCore/Mvvm/ObservableObject.cs` (expõe `SetProperty`/`OnPropertyChanged`); comandos `RelayCommand`/`RelayCommand<T>`/`AsyncRelayCommand` em `src/PixieDownloader/Mvvm/RelayCommand.cs`. Sem geradores de código — toda propriedade observável é explícita (`get`/`set => SetProperty(...)`) e cada comando é uma propriedade pública inicializada no construtor do VM. `CanExecuteChanged` é roteado pelo `CommandManager.RequerySuggested`. A saída tem só 3 DLLs (`PixieDownloader.dll`, `YtDlpCore.dll`, `PixieDownloader.Sdk.dll`).
- **Sem DI container.** A composição é manual no `App.xaml.cs` (`Microsoft.Extensions.Hosting` foi removido de propósito — deixava 27 DLLs inúteis na saída). Grafo: `SessionLogger → SettingsService → YtDlpService → MainViewModel → MainWindow`, disposto no `OnExit`.
- **Settings:** `settings.json` ao lado do `.exe`, auto-save com debounce (`SettingsService`) que depende do `PropertyChanged` borbular dos nós de `AppSettings`. Se mexer em settings, garanta que os setters disparam `PropertyChanged`.
- **Scripts `.ps1` são UTF-8 com BOM:** o Windows PowerShell 5.1 (o `powershell` da máquina — não há `pwsh`) lê `.ps1` sem BOM como ANSI e quebra em qualquer acento/travessão; os scripts também evitam `&&`, `??` e ternário pra rodar igual no 5.1 e no pwsh 7 do runner.
- **Staging de download:** arquivos intermediários do yt-dlp vão pra uma pasta oculta `.~downloads/job-<guid>/` **ao lado do `.exe`** (`-P temp/home`), uma por download; só o arquivo final vai pra pasta de saída. Nada sobrevive a uma saída limpa; sobra = sessão interrompida (avisa e limpa na abertura).
- **Não há botão "Analisar":** a análise dispara sozinha ao colar/digitar uma URL (debounce de 700 ms); Enter na caixa re-analisa. Uma URL nova cancela a análise da anterior.
- **Botão "Cancelar" da aba principal só habilita com download/processamento em andamento** e cancela o primeiro item ativo da fila, não análises.
- **Logo:** `Assets/logo.ico` (embedado como Resource WPF + `ApplicationIcon`). Não há mais `logo.png`.
- Binários `yt-dlp`/`ffmpeg`: resolvidos de `./tools/` ou do PATH. **O que faltar é baixado sozinho na abertura** (`MainViewModel.EnsureToolsAsync`: yt-dlp, depois ffmpeg no build "Completo", sem perguntar); falhou (offline) → fica o ponto vermelho com o botão *Instalar* de sempre. A checagem de atualização do yt-dlp só roda quando ele já existia — o recém-baixado é o último por definição.
